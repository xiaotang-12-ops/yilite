问题本质
现在 Step2 是“逐页 Vision 抽取 → 直接落盘”，缺少字段级 QA + 修复回路（丢了就丢了）。见 core/gemini_pipeline.py (line 406)。
🛠️ 解决方案
【方案 A：双通道 + QA Gate（强烈推荐，最稳）】

思路：Step2 结束后，新增“文本通道校验/补全”：
用 fitz 读 PDF 的文本层，按 BOM 结构把 code -> product_code 再解析一遍；
以 code 为主键 merge：Vision 结果缺的 product_code 用文本通道补齐；
若补齐后仍为空：标为“必须人工确认/必须重跑 Vision（只针对缺失行）”。
优点：不依赖“字符串顺序一致”，因为你解析的是“BOM 行结构”；对标准件规格补全特别有效。
风险：PDF 若无文本层会补不出来；需要 fallback。
【方案 B：只做 QA + 定向返工（改动小）】

思路：不加文本解析，只加“缺字段返工”：
统计缺失的 product_code 行；
重新调用 Vision，但不是让它再抽整页 BOM，而是把“缺失的 code 列表”喂给它，让它只回填这些行的 product_code。
优点：实现最轻，依然能提升完整度。
缺点：成本更高、稳定性仍受模型波动影响。
【方案 C：工程兜底（不改抽取，只改数据治理）】

思路：把 product_code 视为“必填字段”，缺失直接让任务进入“待审核”状态（前端/工程师视图里列出缺失行并提供编辑）。
优点：结果可控、可追责。
缺点：需要人工介入（但对油缸这类“型号不一致”的项其实反而更合理）。

2) 产品级“层级匹配 → AI 匹配”这条流程有没有用？
结论：有用，但它的价值不是“替代 AI”，而是给 AI 加护栏、并把子装配体高亮做成确定性。

为什么有用
层级来自 STEP 的 NAUO 关系，天然能回答：“某个子装配体包含哪些叶子件”。这比 AI 靠语义猜要稳定得多（见 core/step_hierarchy_parser.py (line 23) + core/hierarchical_bom_matcher_v2.py (line 589)）。
实际策略在代码里就是：层级优先 → 再处理剩余零件（见 core/hierarchical_bom_matcher_v2.py (line 395)）。
现在“用起来不够”的关键风险（你 gap report 已经印证）
多实例会漏：当前 _build_assembly_mesh_mapping 的索引是 geom_to_node.setdefault(name, node_name)，同名几何/重复实例会被覆盖成“只留一个”，导致滚筒组件那种 36 件只挂到 1 件（见 core/hierarchical_bom_matcher_v2.py (line 607)；现象见 schemeC_gap_report.json (line 1) 的 unassigned 统计）。
层级文件不带 NAUO：step_assembly_hierarchy.json 只有 name 列表（见 core/step_hierarchy_parser.py (line 93)），你没法把“重复的 child_name”精确落到“哪一个 NAUO 实例”。
🛠️ 可选改进方向（不等于代码匹配）
【方案 A：实例级层级（推荐）】：层级输出/中间结构里带上 NAUOxxx，并且“几何名 → [node_name列表]”而不是单个值；这样层级匹配可以真正覆盖数量。
【方案 B：层级只当约束，AI 只在约束内选】：让 AI 只能在“该装配体的叶子候选集”里分配 BOM 行，避免跨装配体串件（解决 overlap）。
【方案 C：层级用于 QA】：匹配后做一致性检查：某节点分配到的 BOM code 的父装配体是否与 STEP 层级冲突，冲突则打回重分配/人工确认。
