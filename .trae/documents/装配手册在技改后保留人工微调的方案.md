## 我的理解
你要解决的是“工程变更（技改）”在规模化场景下的真实痛点：
- 小改：只换 1-2 个零件（变长/变短也算）→ 3D 变了、装配说明也要变，但用户不想把之前改好的说明全部推倒重来。
- 大改：换掉一半以上零件 → 结果基本是新产品，但仍希望尽量复用旧的编辑成果、并把成本可控。
- 成本：现在重复上传 PDF/STEP 触发 6-Agent 全流程，LLM 调用昂贵；用户有几万套图纸，必须有“少调用、可复用、可批处理”的策略。

## 我的计划
基于现有代码结构（pipeline + 手册草稿/版本存储），我给你一个对用户“立刻更方便”、对系统“显著降 AI 成本”的三档方案：
- A 档：0 AI 调用的“只更新资源”
- B 档：按变更范围的“局部 AI 再生成 + 自动合并”
- C 档：大改时的“全量再生成 + 三方合并保留人工微调”
并配套“缓存/去重”机制，支撑几万套规模。

## 现状诊断（为什么现在用户觉得麻烦、也贵）
### 1）用户麻烦的根因
- 再生成会创建/覆盖/复制一个新的任务目录（output/{task_id} 或 task_id_v_n），旧目录里的 draft/versions 不会自动迁移到新结果。
- 人工编辑是“整份 JSON 覆盖保存”（save-draft / publish / 兼容 put）→ 缺少“把旧编辑迁移到新生成”的合并器。

### 2）AI 成本高的根因
- gemini_pipeline.run() 是单体全流程：Step1-8 一次跑完，Step5/6/7 会触发多次 LLM（尤其组件多时 Step5 循环调用组件 Agent）。
- 当前没有“按组件缓存/复用”或“只对变更组件调用 LLM”的机制。

- 大改时，我们可以做“三方合并”，最大化迁移用户编辑，而不是让用户重编。

## 对用户有什么帮助？（用用户视角描述 3 档功能）

### A 档（最快、最省钱）：只更新 3D/PDF 资源，不改说明文案（0 次 LLM）
适用：零件变长变短但装配工艺不变，用户主要需要“新图/新 3D”。
- 用户操作：在手册页点“技改更新”→ 上传新的 STEP/PDF（只传变更文件）→ 立即生效。
- 系统行为：
  - 只做确定性计算：PDF→图片、STEP→GLB、BOM-3D 匹配更新
  - 不调用 Agent 3/4/5/6，不改用户编辑过的文本
- 用户收益：几乎无等待、成本最低；适合大规模批量更新。

### B 档（推荐解决你说的“小改两零件”）：局部 AI 再生成 + 自动合并（LLM 调用按变更数量计费）
适用：变长变短导致说明确实需要改，但只影响少数组件/步骤。
- 用户操作：
  - 上传新文件后，系统自动识别“哪些组件受影响”（或用户手动勾选受影响组件）
  - 选择“只重算受影响章节”
- 系统行为：
  - 只对受影响组件跑 Step5（组件 Agent）
  - 只对受影响步骤做 Step7 增强（焊接/安全）
  - 其他章节完全复用旧手册（包括用户微调过的文本/插入步骤/排序）
  - 最后把“新生成的受影响章节”替换进旧手册，并生成一份“需要复核清单”
- 用户收益：
  - 只改 2 个零件 → 大部分章节无需重编，AI 调用从“全量组件数”降低到“2 个组件 + 少量增强”。
  - 用户只需要复核受影响章节，工作量从“全本重改”变成“改两章”。

### C 档（大改/换一半以上）：全量再生成 + 三方合并保留人工微调（成本高但不浪费编辑）
适用：变更范围巨大，局部再生成不可靠。
- 用户操作：选择“全量重算（大技改）”。
- 系统行为：照常跑 Step1-8，但不会丢掉旧编辑：
  - old_base（上次生成基线）
  - user_edited（用户已微调的草稿/发布）
  - new_base（这次全量生成）
  三方合并：尽可能把用户编辑迁移到 new_base，并列出冲突（需要人工确认）。
- 用户收益：即便全量重算也不会回到“从零编辑”，而是“少量冲突点复核”。

## 如何把 AI 成本压下去（面向“几万套图纸”的机制）
### 1）任务内增量：按变更文件 hash 识别受影响组件
- 为 output/{task_id} 记录 input_manifest.json：每个 PDF/STEP 的 sha256、对应 component_code/drawing_index。
- 技改上传后，只要 hash 不变就视为“未变”，跳过所有 AI。

### 2）跨任务去重（可选但很值钱）：组件级缓存
- 缓存 key：component_code + pdf_hash + step_hash + model_name
- 缓存 value：agent3 结果（step5_component_results 的单组件片段）、以及 step7 增强结果。
- 命中缓存时：直接复用 JSON，不调用 LLM。

### 3）批处理与预算
- 支持后台队列：让“技改更新”可批量排队执行。
- 支持预算策略：超过阈值（例如 >50% 组件变更）自动建议走 C 档，并提示预计调用次数。

## 风险预判（我会怎么保证不坑用户）
- 受影响范围识别可能不完美：因此 B/C 档一定会输出“待复核清单”，宁可多提示也不静默错合并。
- step_id 每次生成会变：所以合并必须依赖 _legacy_step_id（已在样例中验证存在）。若个别任务缺失 legacy，我会降级为 component_code+step_number 并提高冲突提示。
- 大改本质是新产品：C 档仍需较多 AI 成本，但至少把用户的编辑劳动最大化迁移，避免“成本+人工双重浪费”。

## 验收标准（你确认后我按这个交付）
- 小改（2 个零件变长/变短）：
  - A 档：0 次 LLM，3D/PDF 更新成功，文本不变
  - B 档：只对 2 个组件调用组件 Agent（+必要增强），其他章节用户编辑完全保留；生成待复核清单
- 大改（>50% 组件变化）：
  - C 档：全量生成，但用户已编辑过的字段尽可能迁移；冲突项可定位
- 规模化：同一零件/同一图纸重复出现时缓存命中，LLM 调用次数显著下降
